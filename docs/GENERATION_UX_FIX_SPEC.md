## 2. Блокер генерации

### 2.1 Подтверждённая проблема

Сейчас приложение допускает генерацию по размеру её исходного запроса. Получив черновик, оно строит новый запрос проверки: полный черновик плюс исходный контекст и инструкции. Этот запрос может превысить консервативную границу 4096 ещё **до отправки проверяющей модели**. Потраченный вызов есть, готовой карточки нет, а ошибка приложения выглядит как просьба дополнить исходники.

Таким образом, «модель вызывается», «черновик получен», «проверка отправлена» и «карточка доступна для оценки» — четыре разных события. Успехом фикса нельзя считать первое из них. Личные входы, ответы, скриншоты и context-pack hashes не включаются в публичное доказательство.

### 2.2 Общий план бюджета до первого вызова

Ввести единый доменный план допуска **всего задания**, независимый от React. До запуска модели он учитывает:

- установленную возможность контекста — исходно 4096;
- фактически подготовленный контекст родителей, выбранные свойства референсов, цель сада и одобренные предпочтения;
- полное оформление запроса с используемым model template либо обоснованным резервом на него;
- ограничение вывода генерации и допустимый размер сериализованного черновика;
- последующий запрос проверки, включая этот черновик, необходимые доказательства и собственный вывод;
- возможное исправление формата в любой из стадий с его дополнительными инструкциями.

Успешный допуск означает: **любой валидный черновик в объявленных границах этой попытки может быть передан проверке**. Нельзя сначала разрешить больший ответ, а потом обнаружить, что сам контракт не помещается во вторую стадию.

Когда действительно доступен соответствующий установленной модели tokenizer, использовать его с зафиксированной идентичностью. При его отсутствии оставить честную консервативную верхнюю границу, явно обозначив метод. UTF-8 байты не выдаются за наблюдённые токены. Измерение должно учитывать реально отправляемое представление, а не только строки исходников. Нельзя незаметно увеличить `num_ctx`, обрезать данные у провайдера или скачать tokenizer/веса.

Допустимы версия компактного представления проверки или адаптивные границы черновика, если:

1. сохраняются смысловой минимум карточки, вклад каждого родителя, взаимодействие, действие/выбор/последствие, ограничения и проверяемые reference claims;
2. преобразование детерминировано, версия и пропуски видны; полный оригинал/черновик сохранён;
3. обязательные доказательства не исчезают ради прохождения лимита;
4. ограничения согласованы между prompt, schema, валидатором и обеими стадиями **до генерации**.

Если безопасный план невозможен, попытка не отправляется: нет списанного вызова, попытки, слота или успешной пары. Причина — «Не удалось подготовить запрос в пределах модели», с конкретным доступным действием. Это технический отказ допуска, не ответ модели «не хватает деталей».

### 2.3 Учёт, отрицательные ответы и старые черновики

Обычная попытка — генерация и проверка. Максимум один ремонт формата на всё задание, то есть не более трёх модельных вызовов. Для каждого реального dispatch сохраняются исходный запрос, schema/версии, способ подсчёта, пределы и фактические provider observations. Все сырые ответы и ошибки остаются доступными.

`no_blend`, `no_growth` и модельный `needs_context` остаются допустимыми отрицательными исходами; проверка для них не требуется. Они не превращаются в успех. Ошибка формата, отказ бюджета приложения и запрос дополнительных исходных сведений различаются отдельными причинами. Старое `needs_context` не переписывается задним числом в якобы полученную оценку.

Сохранённые валидные черновики, остановленные перед проверкой, не генерируются заново автоматически. Должна быть возможность явно проверить прежний точный текст новым допустимым планом: сохранить первоначальные ответы/ошибки и добавить новую оценку с её датой и происхождением. Повторная проверка расходует свой реальный вызов, не возвращает предыдущие расходы и не создаёт дубликат пары/карточки. Положительная оценка или явное человеческое решение по-прежнему необходимы для соответствующего перехода; фиктивный pass запрещён.

## 3. Две кнопки в верхней части главного окна

Общая верхняя панель доступна на всех основных экранах. В ней ровно две главные команды: **«Пауза / Продолжить»** и **«Эврика»**. Рядом видны выбранный сад и короткий фактический статус. Кнопки не должны теряться в прокрутке бокового меню или в настройках отдельного сада.

### 3.1 «Пауза / Продолжить» — на всё приложение

| Состояние                                     | Кнопка и действие                                                                                                              |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Расписание включено, ожидание таймера         | «Пауза» — остановить автозапуск во всех садах                                                                                  |
| Идёт генерация или проверка                   | «Пауза» — отменить текущее задание, дождаться остановки и освободить собственную модель                                        |
| Автозапуск на паузе, но идёт разовая «Эврика» | «Пауза» — остановить и эту разовую работу                                                                                      |
| Идёт отмена/освобождение                      | «Останавливаем…»; повторная команда недоступна с видимой причиной                                                              |
| Всё остановлено                               | «Продолжить» — возобновить расписание ранее включённых садов                                                                   |
| Есть препятствие безопасному продолжению      | Понятная причина и действие для устранения; кнопка не должна скрыто сбрасывать ошибки сохранения или утраченное доказательство |

«На паузе» показывается только после подтверждённого прекращения работы/освобождения модели. Во время остановки не разрешаются новые dispatch или поздний commit. Не затрагиваются чужие процессы и shared runtime.

Продолжение сохраняет интервалы, выбранные сады, кредиты, лимиты и разрешения обмена. Оно не включает ранее исключённые сады, не восполняет пропущенные запуски и не создаёт пачку заданий после сна. Если ни один сад не включён в расписание, интерфейс сообщает об этом и ведёт к выбору садов. Обычный запуск приложения и пробуждение остаются на паузе, как раньше.

Удалить из рабочей панели дублирующую глобальную команду «Разрешить фон». Участие конкретного сада — отдельная понятная настройка «Включать этот сад в расписание», а не второе разрешение на всю модель. Трей, верхняя панель и API управляют одним состоянием контроллера.

### 3.2 «Эврика» — одна попытка прямо сейчас

- Цель — **выбранный сад**. Перед нажатием понятно, для какого сада будет создана идея. Переключение сада после старта не меняет родителей или цель уже идущего задания.
- Пропускается только ожидание интервала. Выполняется обычный исправленный конвейер генерации и проверки, а не упрощённый или всегда успешный путь.
- Работает как явно разрешённый разовый запуск при глобальной паузе и при исключении сада из расписания. После него автоматическое расписание само не включается.
- Сохраняются кредиты и общие лимиты попыток, кандидатов, вызовов и очереди просмотра. При недостаточном бюджете/контексте причина видна до отправки. Честный отрицательный исход возможен; кнопка не обещает гарантированно полезный результат.
- Если модель занята, не создаётся скрытая очередь. Кнопка недоступна с пояснением, какой сад и стадия сейчас выполняются. Пользователь может дождаться завершения или нажать общую паузу.
- Используется разрешённый сохранённый selection plan. Если его ещё нет, один seeded draw выбирает маршрут по настроенной вероятности обмена; план сохраняется до отправки. Разовый триггер и вероятностный выбор маршрута записываются раздельно. При 10% это один шанс на попытку, не обещание каждого десятого результата. Ручное указание конкретной пары остаётся отдельным режимом.
- Нет повторного броска при refresh/retry и скрытого перехода с cross на local. Заблокированный маршрут сохраняет причину и требует явного изменения условий/отмены. Проверки донорства, участия, ревизий и согласий выполняются перед стадиями и commit; p0 не читает донорское содержание.
- Успешный commit тратит один кредит и фиксирует пару/карточку атомарно. Ошибка, отмена и отрицательный ответ кредит сохраняют. Расходы реальных вызовов не возвращаются.
- Повторный клик, сетевой повтор той же команды и столкновение с таймером не запускают второе задание. Нужна сохраняемая идентичность запроса. Повтор прежнего запроса после рестарта возвращает прежнее состояние, а не начинает новую генерацию.
- После фактического разового dispatch следующий автоматический срок этого сада отсчитывается от него, чтобы таймер не запускал соседнюю дублирующую попытку. Остальные сады не теряют свою очередь.

## 4. Райтингу нужна полная переработка

### 4.1 Принцип

Каждое основное сообщение отвечает: **что происходит, где результат, что можно сделать дальше**. Названия внутренних стадий, raw errors и JSON остаются в раскрываемых технических подробностях. Ограничения и происхождение сохраняются, но не заменяют нормальный заголовок страницы защитной оговоркой.

| Ситуация                                   | Основное сообщение и действие                                                                   |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Ждём интервал                              | «Следующая попытка в саду „Игры“ — в 16:40»; локальное время                                    |
| Подготовка/генерация                       | «Создаём идею для сада „Игры“»; фактическая стадия без выдуманного процента                     |
| Проверка отправлена                        | «Проверяем, как сочетаются исходные идеи»                                                       |
| Черновик сохранён, проверка не запустилась | «Черновик создан, но не проверен» + техническая причина и «Посмотреть черновик»                 |
| Модель просит детали                       | «Для этой пары не хватило деталей» + конкретные недостающие сведения, если модель их указала    |
| Честный отрицательный результат            | «Эти идеи не удалось объединить» + сохранённая содержательная причина                           |
| Модель вернула вместо причины только код   | «Модель не объяснила причину»; не выдумывать объяснение за неё                                  |
| Нет карточек на просмотр                   | Сколько было попыток/черновиков, куда они попали, когда следующая попытка и ссылка на черновики |
| Автозапуск остановлен                      | «Автозапуск на паузе» + состояние текущей разовой работы, если она есть                         |

Фразы — направление для редакторской проработки, не требование дословно подставить шаблоны вместо смысла. Модельный и пользовательский текст не переводится/не исправляется молча. Происхождение «сгенерировано на этом компьютере», «импортировано», «записанный пример», «изменено человеком», «принято вопреки проверке» различается понятными словами.

### 4.2 Полный аудит

Переписать тексты исходников и подготовки, референсов/ДНК, генерации, черновиков, просмотра, роста, настроек, резервирования/восстановления и ошибок оператора. Обновить не только заголовки, но и подписи полей, подсказки, пустые состояния, disabled-причины и accessible names. Примеры «+ Сад», «Имя», «ремонт», «локальное наблюдение», «успешная пара», `blend`, `needs_context`, `Waiting for interval` не должны оставаться основным объяснением задачи.

В рабочих экранах не показывать английские технические строки и UTC ISO-время вместо локального времени. Хранение UTC/timezone остаётся точным. Общий статус не приписывает работу выбранному саду, если модель занята другим.

Показать реальную воронку с определёнными знаменателями: попытки → сохранённые черновики → отправленные проверки → результаты проверки → новые карточки для просмотра. Отличать её от старых карточек и человеческих Keep/Develop/Reject. Слоты, дневные расходы и очередь просмотра — разные величины с коротким объяснением; подробная бухгалтерия доступна отдельно.

## 5. Визуальное оформление

Сохранить спокойную садовую палитру, локальную лицензированную типографику и существующий знак. Ввести согласованные стили для обычных/основных/опасных кнопок, селекторов, полей, textarea, checkbox, disclosures и скроллбаров: размеры, отступы, радиусы, границы, контраст, hover/pressed/disabled/focus/error.

Убрать доминирующую стандартную серую полосу бокового меню. Стильно оформить track/thumb/hover и прокрутку основного содержания/диалогов, сохранив удобную зону захвата и wheel/trackpad. Навигация и нижние команды остаются доступны; не создавать вложенную прокрутку без необходимости.

У селекторов должны быть согласованные закрытое состояние и стрелка. Если нужен собственный popup/combobox, он обязан сохранить клавиатуру и screen-reader semantics. Декоративные div вместо доступных controls недопустимы.

Приёмка: 430px native minimum, 200% текста, видимый focus, Tab/Shift-Tab, стрелки, Enter/Space/Escape, forced colors, reduced motion. Статус не передаётся только цветом или анимацией. Никаких внешних шрифтов/ассетов, настройки ОС или новых сервисов для оформления.

## 6. Данные и прямой операторский доступ

Все действия доступны Codex через [локальный операторский API](https://github.com/drevendev/CompostClub/blob/37113d639700d893d36cf8218728b3b68a08d58b/docs/OPERATOR.md). UI и API вызывают одну доменную команду: пауза, продолжение, разовая «Эврика» с request identity и чтение её состояния. Настройка не требует Computer Use, кликов или нативных диалогов. Сохранить capability-проверку, ограничение размеров, сериализацию команд и безопасное закрытие канала.

Обновление сохраняет ID садов/исходников/карточек, полные файлы, ревизии, предыдущие решения и заметки, raw receipts, оплаченные вызовы, источник/manifest обмена и provenance. Новые поля плана допуска и request identity совместимы со старым schema-3 состоянием через явные defaults/версию. Исторические записи не объявляются проверенными новым контрактом.

Сохранить текущие настройки: ёмкость десять слотов на сад, интервал 15 минут, вероятность 10%, взаимное донорство и установленные общие ограничения. Не сбрасывать участие исходников, не расширять его молча и не менять ревизию оригинала ради токенов. Автоматизация не может создавать одобрение человеком, обходить фильтр или скрыто расходовать больше ресурсов.

Перед заменой — согласованная проверенная приватная копия и сохранённый предыдущий executable. Откат не смешивает SQLite/WAL разных версий. Личные тексты, paths, скриншоты, raw ответы и pack hashes остаются вне публичных issues, fixtures, CI и архивов исходников.

## 7. Приёмка

### 7.1 Детерминированная матрица

| Область            | Обязательные сценарии                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бюджет двух стадий | RU/EN, длинные evidence ID, reference facts, границы input/output, полный допустимый черновик и оформление обоих запросов                         |
| Отказ допуска      | До первого dispatch нет расходов/слота/пары; техническая причина не маскируется под ответ модели                                                  |
| Ремонт             | Ошибка генерации или проверки, один общий ремонт, недостаток 1/2/3 вызовов, сохранение обеих причин и оригиналов                                  |
| Исходы             | Кандидат/pass, проверка с замечаниями, no_blend/no_growth, модельный needs_context, неправильная ссылка/evidence, обрыв/timeout                   |
| «Эврика»           | На паузе и при расписании, выбранный сад, не включённый в расписание сад, занятый model owner, отсутствие кредита/лимита/контекста                |
| Дубликаты          | Двойной клик, повтор request ID, потерянный ответ, рестарт, одновременный таймер, точное одно списание                                            |
| Обмен              | 0/10/100%, сохранённый маршрут, отсутствие fallback/reroll, один донор, revocation между стадиями                                                 |
| Глобальная пауза   | Ожидание, генерация, проверка, разовая работа из паузы, остановка/освобождение, запрет позднего dispatch/commit                                   |
| Расписание         | Два сада, справедливость, следующий срок после «Эврики», отсутствие catch-up после сна/возобновления                                              |
| Данные             | Обновление/рестарт/backup/restore со старыми карточками, полный raw и решения, прежний долг вызовов, отсутствие дубликатов при повторной проверке |
| UX                 | Понятные пустые состояния, правильный сад/часовой пояс, стабильные кнопки, раскрываемые технические подробности                                   |
| Native             | Точный packaged EXE, настоящий PID, отсутствие destroyed-WebContents popup, pause/Exit в обеих стадиях, следующий запуск на паузе                 |

Двойники и ускоренное время явно обозначаются диагностикой. Нельзя снова засчитать только оплату/наличие модельных вызовов как работающую генерацию.

### 7.2 Настоящий локальный результат

До изменения prompt/контракта зафиксировать новый небольшой набор: восемь совместимых пар (четыре RU, четыре EN) и два несовместимых/неполных контроля, с независимыми вымышленными текстами, вкладом родителей и рубрикой. Ранее увиденные случаи — регрессии, не переименованный holdout. Не более двух вариантов prompt в сравнении; один исходный ответ на случай/вариант, не более трёх вызовов на задание, все исходы и расходы сохраняются. Максимум этого фиксированного сравнения — 60 реальных вызовов в явно настроенном изолированном профиле.

На установленной локальной модели доказать:

- генерация и проверка действительно отправлены; нет provider truncation или постфактум-отказа проверки для валидного допущенного черновика;
- как минимум одна новая RU- и одна EN-карточка проходят обязательную проверку и реально появляются в интерфейсе просмотра;
- эти карточки не являются recordings, заглушками или человеческим override; человеческая оценка полезности пока неизвестна;
- отрицательные контроли остаются честными отрицательными/контекстными исходами, а не выданными за успех;
- разовая «Эврика», проверка старого черновика, оба сада, пауза и API ведут себя по описанным правилам;
- сохраняются все отфильтрованные/невалидные ответы, реальные stage/job latency, токены там, где наблюдены, и подтверждение освобождения ресурсов.

Если модель на этом фиксированном наборе не даёт указанные реальные карточки, фикс нельзя объявить готовым для обещания «генерация работает». Нельзя добиваться зелёного результата снятием проверки или скрытием неудачных случаев. Эти технические критерии не подменяют полную owner-usefulness/R8 приёмку из [основной спецификации](NEXT_RELEASE_SPEC.md).

### 7.3 Уточнения по результатам ревью

- **Повторы команд:** request ID связывается с садом и неизменяемыми параметрами. Тот же ID с другим содержимым возвращает конфликт. При потерянном ответе клиент запрашивает состояние, а не создаёт новый ID автоматически. Сбой после dispatch не доказывает отсутствие расхода: сохраняется неопределённый исход, оплаченный вызов не возвращается. Незавершённая работа после рестарта не возобновляется сама; успешный атомарный commit обнаруживается без повторного списания.
- **Старый черновик:** повторная проверка привязана к точным сохранённым ревизиям и доказательствам. До отправки и commit повторно проверяются доступность доказательств, актуальные разрешения, отсутствие уже использованной пары, свободный слот и дневной бюджет. Изменение исходника не подменяет прежний текст. При запрете доступа или отсутствии обязательного контекста предлагается явная новая попытка; автоматической подмены или обхода проверки нет. Человеческое принятие вопреки проверке остаётся отдельным явно отмеченным действием и не засчитывается в техническую приёмку RU/EN.
- **Остановка и неопределённость:** задать конечный timeout каждой стадии и остановки в контракте контроллера; записывать фактическую длительность. При невозможности подтвердить освобождение ресурсов показывать «Не удалось подтвердить остановку», запрещать новый dispatch и предлагать безопасное действие. Нельзя бесконечно показывать «Останавливаем…» или ошибочно объявлять паузу.
- **Без холостого нагрева:** ожидание интервала и чтение статуса не запускают inference, повторные клики не загружают модель. Детерминированный отказ допуска блокирует повтор того же плана до изменения значимых условий и показывает причину. Ошибки не создают tight loop или незаявленные автоматические повторы; отрицательный ответ модели допускает только следующую штатную попытку по расписанию. Проверить это по реальным dispatch и жизненному циклу процесса, а не по цвету кнопки.
- **Честная оценка:** совместимость фиксированных пар — ожидаемая рубрика, а не предписанный ответ модели. Изменения prompt после просмотра результатов документируются как разработка; увиденные случаи больше не называются независимой проверкой. Лимит 60 относится к сравнению вариантов; дополнительные native/operator проверки учитываются отдельно с заранее указанным ограничением, без расходования личного бюджета садов.
- **Сохранность при откате:** сверка до/после включает идентификаторы и содержимое оригиналов, ревизии, связи карточек, решения, заметки и накопленные расходы. Старый executable запускается только с совместимой проверенной копией данных; возврат к прежнему snapshot не должен скрыто уничтожать новые результаты. При несовместимости нужен проверенный перенос или явный выбор владельца, а не автоматическая потеря записей.

Эти сценарии входят в матрицу §7.1 и обязательны для закрытия соответствующих задач.

## 8. Поставка и критерий завершения

Пока блокер открыт, не тратить unattended compute на заведомо недопускаемый второй этап. Сначала проверить backup, затем выполнить исправление и тесты. Требуемые команды: `npm run verify`, `npm run docs:check`, `npm run build`, `npm run package:single`, применимые Chromium recovery/P1/sample suites и actual native/operator acceptance точного portable. Проверить сохранность прежних данных на приватной копии и после штатного обновления.

Поставка содержит portable identity, проверенный **recorded** HTML с SHA-256, полный явно отобранный архив исходников с manifest/identity, новую документацию API/карточки и честный отчёт ограничений. Предыдущая сборка и согласованная копия данных остаются доступными. Новый runtime/model, публикация GitHub Release, deployment и изменение других репозиториев отдельно не разрешаются этим документом.

После успешной технической приёмки восстановить разрешённый владельцем режим обоих садов через API и проверить фактический dispatch/результат, сохранив настройки. Обычный последующий restart/wake всё равно начинается с паузы.

**Готово** означает одновременно: P0 устранён, настоящие RU/EN-карточки видны, две верхние команды работают через UI и API, пользователь понимает состояние, controls доступны и оформлены, данные сохранены, точная поставка проверена. До этого issues и соответствующие gates остаются открытыми.
